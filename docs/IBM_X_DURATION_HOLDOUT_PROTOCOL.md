# Frozen X-duration holdout against standard DD

This protocol was written after the completed [characterization](IBM_X_DURATION_CHARACTERIZATION_PROTOCOL.md) and before submitting the held-out job. In the training job, qubit 1's `xslow` X-basis return rate exceeded the equal-duration `x`-plus-wait control at 32 gates in all three blocks, by 0.0120 overall, but a shot-only 95% interval included zero. Fast `x` without equal-duration waiting was substantially better. Qubit 1 and the new lengths below are therefore a **training-selected** follow-up, not an independently selected device-wide primary hypothesis.

- Backend: `ibm_marrakesh`, existing free Open instance; physical qubit 1. No paid execution.
- Held-out even X counts: 16 and 48. State/measurement bases: X and Z. Three randomized complete blocks, 2,048 shots per circuit. The ideal return bit is always `0`.
- Four equal-nominal-duration policies per gate count: `slow` (native `xslow`); `padded` (native `x` followed by a 964-ns delay after every gate); `fast_tail` (all native `x` gates followed by one combined delay); and `dd_tail` (the fast-tail circuit processed by IBM/Qiskit's ALAP schedule analysis and standard two-X `PadDynamicalDecoupling` pass). The DD source tail is shortened by 72 ns to account for its two added 36-ns X gates; compiled total duration is checked for equality. All four target the same unitary. Use optimization level 0, fixed physical layout, and verify the compiled gate/delay counts and durations. Explicitly disable Runtime DD, twirling, and mitigation so no hidden processing differs between policies.
- Prespecified primary endpoint: X-basis return probability at 48 gates. `xslow` constitutes a **candidate physical improvement over established controls** only if `slow-fast_tail` and `slow-dd_tail` are positive in all three blocks and both shot-only 95% lower bounds exceed zero. `slow-padded` and all 16-gate/Z-basis contrasts are secondary. If this criterion fails, report failure. These shot-only intervals exclude time drift; no significance claim follows from them alone.
- Even a positive result would validate only selection between two supported X implementations at one device/time. It would **not** validate the manuscript's continuous inverse-duration law, its GP optimizer, or a broad compiler advantage. Those still require multiple measured gate-duration choices, a prespecified GP policy, and comparisons on independent circuit families.
- Save pre-submit prediction/protocol lock, exact QPY and QASM where exportable, randomized order, job ID/status, raw counts, all comparisons and block results. Job execution cap: 90 seconds.
